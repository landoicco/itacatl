# Theming and verticals

itacatl is one codebase for many kinds of food businesses. **A deployment serves one vertical** (ice cream shops, family eateries, bakeries…), and everything that makes a vertical look and read like itself is configuration, not code. This guide covers the visual part, the theme, and how a new vertical is assembled.

## What a vertical is made of

| Part | Where | Ice cream shops (the demo) |
|---|---|---|
| **Theme**: colors, fonts, shapes, decorations | `frontend/src/theme/`, `VITE_THEME` | `pastel` |
| **Sample data**: businesses, catalogs, menus | `backend/src/main/resources/seed/`, `ITACATL_SEED_FILE` | `ice-cream-shops.en.json`, `.es-MX.json` |
| **Language** | `VITE_DEFAULT_LOCALE` ([i18n guide](i18n.md)) | `en` in the repository, `es-MX` in Mexico |
| **Copy**: headline, item wording | Locale catalogs | "Pick a scoop, we'll save it for you" |

The screens, the API and the domain model are the same for every vertical. A *fonda* publishing its *comida corrida* and an ice cream shop publishing today's flavors use the same menus, items and stock rules ([domain model](domain-model.md)).

## How themes work

### Design tokens

Components never use a raw color, font or radius. They use **semantic utilities** generated by Tailwind from CSS variables:

```tsx
<article className="rounded-card border-theme bg-surface p-4 shadow-card">
  <h3 className="text-display">…</h3>
  <span className="text-low">Only 3 left</span>
</article>
```

`frontend/src/theme/themes.css` defines each theme as a block of `--theme-*` variables, selected by an attribute on `<html>`:

```css
[data-theme="pastel"] { --theme-accent: #7a2e8f; --theme-radius-card: 24px; --theme-shadow-card: 0 4px 16px …; }
[data-theme="market"] { --theme-accent: #c2185b; --theme-radius-card: 16px; --theme-shadow-card: 4px 4px 0 #23160f; }
```

and maps them to Tailwind's theme with `@theme inline`:

```css
@theme inline {
  --color-accent: var(--theme-accent);   /* generates bg-accent, text-accent… */
  --radius-card: var(--theme-radius-card); /* generates rounded-card */
}
```

`inline` makes each utility reference the variable itself (`background: var(--theme-accent)`) instead of copying its value, so changing `data-theme` restyles the whole app at runtime without rebuilding the CSS.

| Token group | Utilities | What changes between themes |
|---|---|---|
| Colors | `bg-page`, `bg-surface`, `text-ink`, `text-muted`, `bg-accent`, `text-on-accent`, `bg-soft`, `bg-open`, `bg-soon`, `text-low` | Palette, status colors |
| Type | `text-display`, `font-body` | Display family, weight and tracking; body family |
| Shape | `rounded-card`, `rounded-control`, `border-theme` | Corner radius, outlined or borderless |
| Depth | `shadow-card`, `shadow-pressed` | Soft shadows or hard "sign painter" offsets |
| Palette | `--theme-scoop-0` … `--theme-scoop-7` | Item colors (below) |

### Choosing the theme

`frontend/src/theme/theme.ts` holds the registry and picks the theme:

1. **The deployment's theme**, `VITE_THEME`, inlined at build time. Unset or unknown values fall back to `pastel`.
2. **In development only**, `?theme=market` in the URL overrides it, to compare themes or take screenshots. Production builds ignore the parameter: a theme is the vertical's identity, not a user setting (unlike the language).

`main.tsx` applies it with `applyTheme(resolveTheme())` **before the first render**, so the page never flashes another theme.

### What CSS cannot express

Some theme differences are structure, not values. The registry in `theme.ts` declares them:

```ts
export const THEMES = {
  pastel: { decorations: { papelPicado: false } },
  market: { decorations: { papelPicado: true } },
} as const;
```

`PapelPicado` renders the market theme's banner of cut paper flags only when the active theme declares it, colored from the theme's palette.

### Item colors

Items have no color of their own, yet the UI shows a colored circle per item. `flavorColor(name)` hashes the item's name (FNV-1a) into one of the theme's eight palette slots:

- **Stable:** the same item always gets the same color, on every visit, without storing anything.
- **Themeable:** the result is `var(--theme-scoop-N)`, so each theme brings its own palette.
- **Limitation:** the color is not semantic (a lime sorbet may come out pink). If businesses want to choose, it becomes an optional field of the catalog item.

### Fonts

Fonts are bundled with the app through `@fontsource` packages (`frontend/src/theme/fonts.ts`) instead of loaded from Google Fonts: no third-party request with the user's IP, no dependency on another service at runtime, and Vite gives the files content hashes for permanent caching. Every theme's fonts are declared, but the browser only downloads the files that rendered text uses.

## How to

### Add a theme

1. Add a `[data-theme="<name>"]` block to `themes.css` that defines **every** `--theme-*` variable of the existing themes, including the eight palette slots.
2. Add it to `THEMES` in `theme.ts`, with its decorations.
3. If it uses new fonts, add their `@fontsource` packages and imports in `fonts.ts`.
4. Try it with `npm run dev` and `?theme=<name>`; ship it with `VITE_THEME=<name>`.

Components need no change. If a theme needs a new token, add it to every theme and to `@theme inline`, then use the utility.

### Add a vertical

1. A theme (above), or reuse one.
2. Seed files in English and Spanish, with the same item keys (format: [domain model](domain-model.md#sample-data)).
3. The vertical's copy in the locale catalogs.
4. A deployment built with its `VITE_THEME` and `VITE_DEFAULT_LOCALE`, and started with its `ITACATL_SEED_FILE`.

## Tests

`frontend/src/theme/theme.test.ts` checks that item colors are stable and always point to a palette slot, that unknown themes fall back to the default, and that every theme declares its decorations.
